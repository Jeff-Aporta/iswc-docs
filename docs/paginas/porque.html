Fundamentos

Por qué existe

Toda documentación de API que se mantiene aparte del código acaba mintiendo. No por descuido: porque son dos artefactos distintos que nadie obliga a decir lo mismo.

El problema no es escribir la documentación

Escribirla es la parte fácil. El problema es que a los dos meses el endpoint acepta un parámetro nuevo, la colección de Postman sigue con el viejo, y nadie se entera hasta que alguien pierde media tarde depurando una petición que nunca iba a funcionar.

Ese fallo tiene una forma muy concreta y se repite en todas partes: el artefacto se genera bien y el contenido está mal. La colección se abre, el visor pinta, el JSON valida. Solo que describe una API que ya no existe.

Es el mismo patrón que gobierna las pruebas de este proyecto: lo que se vigila no es que algo funcione, sino que dos fuentes que deberían decir lo mismo no se hayan separado.

Dónde se rompe la cadena

Tres pasos manuales entre el cambio y quien lo consume. Cada uno se puede olvidar sin que ningún proceso avise.

La apuesta: una sola fuente, servida en vivo

El backend de InSoft ya publica su propia configuración en /system/swagger/config.json: rutas, parámetros, catálogos, documentación y hasta qué endpoints exigen sesión. Ese documento no es una copia de nada — es lo que el servidor sabe de sí mismo.

IS-Swagger no mantiene un catálogo propio. Lee ese endpoint cada vez que se abre. Si el backend cambió esta mañana, el visor lo enseña esta mañana, sin que nadie exporte ni reimporte nada.

Catálogo mantenido a mano

  • Dos artefactos que hay que sincronizar.
  • El desfase no da ningún error.
  • Se comparte por archivo: cada copia envejece por su lado.
  • Quien lo recibe necesita instalar el cliente.

Servido por el propio backend

  • Una sola fuente: la que el servidor ya publica.
  • No hay desfase posible porque no hay copia.
  • Se comparte por enlace: siempre trae lo último.
  • Quien lo recibe abre una URL.

Por qué no bastaba Swagger UI

Swagger UI resuelve la mitad: lee un OpenAPI y lo pinta. Pero el documento de InSoft no es OpenAPI — trae catálogos de valores, documentación en Markdown por endpoint, subgrupos con orden propio y reglas de sesión que OpenAPI no sabe expresar.

Se podía traducir a OpenAPI y perder esa información, o leer el formato real y aprovecharlo entero. IS-Swagger hace lo segundo: traduce el documento InSoft a su propia estructura interna, y por eso puede pintar un selector con los valores válidos donde Swagger UI solo pintaría una caja de texto.

Consecuencia deliberada: la palabra «OpenAPI» no aparece en la interfaz. Es un formato que el visor acepta, no lo que el visor es. Hay una prueba que falla si se cuela en la UI.

Y por qué no bastaba el visor anterior

La primera versión era React + MUI + Babel en el navegador. Funcionaba, pero para incrustarla había que arrastrar React, ReactDOM, MUI, Emotion y un transpilador que compilaba en cada carga. Abrir el HTML suelto no servía de nada.

Para una herramienta cuyo valor es «te lo mando por enlace y lo abres», ese peso era el defecto principal, no un detalle. El stack actual nació de quitarlo.
