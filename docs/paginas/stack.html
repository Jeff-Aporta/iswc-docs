Stack

TypeScript sin bundler, web components sin framework

El único runtime es el navegador. No hay React, no hay MUI y no hay Babel compilando en cada carga. Lo que el navegador recibe son módulos ES planos y hojas de estilo normales.

El cambio frente al visor anterior

Capa Antes (React) Ahora
Interfaz React 18 + MUI 5 + Emotion Web components vanilla + kit is-* por CDN
Transpilación Babel en el navegador esbuild en build; el navegador recibe ESM plano
Fuente .jsx .ts — solo se borran los tipos, sin empaquetar
Estilos Emotion sx + un .css global Un .css hermano por componente, en su shadow
Estado Context + hooks repartidos Un solo dueño (sw-app), hijos controlados
Distribución 4 bundles + vendor CJS dist/cdn/ plano: un .js y un .css por módulo

El build: transpila, no empaqueta

scripts/build.mjs pasa cada .ts por esbuild de forma independiente. esbuild solo le quita los tipos y lo minifica: no resuelve dependencias, no hace tree-shaking, no produce un bundle.

La salida se aplana a un único directorio, y los imports relativos se reescriben para que todo módulo sea hermano de todos. Eso es lo que permite servir dist/cdn/ desde cualquier sitio — un CDN, un worker, una carpeta — sin que nada tenga que resolver rutas.

El .css no pasa por el compilador de TypeScript: se minifica y se copia al lado de su módulo. Ese emparejamiento es el contrato del que vive adoptCss.

El contrato del CSS

Cada componente tiene su hoja hermana. El módulo la reclama con adoptCss(shadow, import.meta.url), que deriva sw-operation.css de sw-operation.js — nadie tiene que declarar la relación en ningún sitio. 

src/components/sw/sw-operation.ts
src/components/sw/sw-operation.css
        ↓ build
dist/cdn/components/sw/sw-operation.js
dist/cdn/sw-operation.css

La hoja se aplica como CSSStyleSheet construida y cacheada por URL, no como <link>. Es una diferencia que se ve: un <link> dentro de un shadow root no bloquea el pintado de ese shadow, así que el navegador pinta sin estilos y recoloca al resolver la hoja. Con decenas de shadow roots eso es un parpadeo visible en cada cambio de sección.

Regla dura: el CSS nunca vive dentro del .ts. Metido en una constante no se minifica aparte, no se cachea aparte y ninguna herramienta de CSS lo ve. Es un error que este proyecto heredó de un hermano y que hoy vigila una prueba.

Las piezas

TypeScript estricto

strict + noUncheckedIndexedAccess. Los tipos son ambiente (src/types/): visibles sin importar nada.

Web components

Shadow DOM y customElements nativos. Un componente es una clase que pinta, sin ciclo de vida de framework.

Kit is-* por CDN

Botones, diálogos, campos, tablas, toasts e iconos ya resueltos. No se reinventa ninguno.

esbuild

Única dependencia de build junto a TypeScript y jsdom. El build entero tarda menos de un segundo.

deno test

Sin runner externo. Las pruebas corren contra dist/cdn/: lo que rompe en producción es el artefacto.

Tokens del kit

Todo el color sale de --is-*. Cambiar de tema o de paleta recorre el visor entero sin tocar un componente.

Lo que se ejecuta

deno install
deno task build      # src/**.ts → dist/cdn/*.js (+ *.css copiados)
deno task dev        # el mismo build en watch
deno task check  # tsc --noEmit
deno task test           # build + deno test tests/

Dos archivos quedan fuera del pipeline de TypeScript a propósito: src/js/boot.ts y src/js/hojas.ts. Corren síncronos en <head>, antes de que exista ningún módulo, para aplicar el tema y preparar la caché de hojas sin parpadeo.
